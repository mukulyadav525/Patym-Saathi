PAYTM SAATHI — TECHNICAL REQUIREMENTS DOCUMENT
Version: Hackathon MVP v1.1 (aligned to deck TeamAIR01.pdf)
Architecture: Expo React Native Android app + Next.js web dashboard +
FastAPI + Supabase PostgreSQL + Sarvam AI adapters + Paytm adapter (DEMO
default).

1. ARCHITECTURE (deck slide 13)
Channels: Android merchant app (text + in-app voice), web dashboard.
Both call the same FastAPI API over HTTPS.
AI Soundbox is a proposed channel; not built.

Saathi core (FastAPI):
- Speech I/O: Saaras (STT), Bulbul (TTS) via server-side Sarvam adapter.
- Orchestrator: intent extraction (Sarvam LLM, rule-based fallback) and
  calls to the typed tool registry (§8).
- Policy engine: action tiers, budget caps, approval tokens.
- Evidence builder: attaches source records to every plan/brief.
- Task tracker: state machines (§5), retries.
- Audit log: append-only record of plans, approvals, adapter calls.

Tools/connectors (adapters): Paytm (DEMO | STAGING), Billing/POS (SAMPLE
seed data), Inventory (SAMPLE seed data), Suppliers (SIMULATED).

Data: Supabase PostgreSQL (region ap-south-1 Mumbai) is the system of
record. No Redis and no separate event queue in the MVP: webhooks are
written to payment_events and processed in the same request (or a
FastAPI BackgroundTask) to advance the task. Approval tokens live in the
approvals table. (Deck slide 15 lists Redis — see checklist §10.)

Clients never talk to Supabase tables directly; all data goes through
FastAPI. Supabase Auth issues the JWT; FastAPI verifies it.

5. STATE MACHINES
Task:
NEW -> UNDERSTANDING -> EVIDENCE_READY -> PLAN_DRAFTED ->
AWAITING_APPROVAL -> APPROVED -> EXECUTING -> VERIFYING -> COMPLETED
Exception: EXECUTING -> EXCEPTION -> PLAN_DRAFTED (new plan version) ->
AWAITING_APPROVAL ...
Terminal: COMPLETED, PARTIALLY_COMPLETED (approval 2 rejected),
CANCELLED (approval 1 rejected/expired), FAILED.
BRIEF: NEW -> UNDERSTANDING -> EVIDENCE_READY -> COMPLETED (no approval).
Restock VERIFYING = waiting for goods receipt; COLLECT_DUE VERIFYING =
waiting for verified payment.

Order: DRAFT -> AWAITING_APPROVAL -> APPROVED -> SUBMITTED ->
ACCEPTED | PARTIALLY_ACCEPTED -> GOODS_RECEIVED; or CANCELLED / FAILED.
SIMULATED is shown via connector_mode, not as a state. Never
GOODS_RECEIVED on creation.

Invoice (deck slide 10):
PENDING -> DRAFTED -> APPROVED -> SENT -> VERIFIED -> PAID
Side states: FAILED, EXPIRED, CANCELLED, REFUNDED,
RECONCILIATION_REQUIRED. Only the verification path (§9) moves an
invoice to VERIFIED/PAID.

Every transition: validated against an allowed-transitions table, done
in a DB transaction, and writes an audit_event.

6. RESTOCK CALCULATION (deterministic, backend only)
horizon_days = 7 (next restock cycle covering the weekend)
forecast = ceil(avg weekly packs_sold over last 4 weeks * horizon/7)
safety_stock = 0 in demo (config RESTOCK_SAFETY_PACKS)
net_need = max(0, forecast + safety - usable_packs - inbound_packs)
order_packs = round_up(net_need, max(pack_size, min_order_packs))
Supplier choice per line: cheapest valid quote (not expired, enough
available_packs); tie -> fewer suppliers.
Budget: if committed_total + new total > budget, return BUDGET_EXCEEDED
with options (drop lowest-priority line / reduce qty); never exceed.
Re-plan: keep accepted lines as committed; re-source unavailable lines
(partial at same supplier first, then alternative supplier); new plan
version with diff vs previous.
The LLM never computes or edits quantities or totals.

7. APPROVAL SECURITY
- Authenticated user with OWNER membership for the merchant.
- Approval sheet shows supplier(s), each line (item, packs, unit ₹,
  line ₹), total, budget, remaining budget, and the diff vs the previous
  approval.
- payload_hash = SHA-256 of canonical JSON {merchant_id, task_id,
  plan_id, plan_version, action_type, suppliers, lines, currency, total,
  budget}.
- POST /approvals/{id}/confirm: recompute hash from current DB state,
  check not expired (10 min), status PENDING, quotes still valid, then in
  one transaction mark CONSUMED and execute. Single-use.
- New plan version -> previous PENDING approvals SUPERSEDED.
- Voice is never an authorization factor. Optional 4-digit PIN.
- Duplicate confirm with the same Idempotency-Key returns the first
  result.

8. AGENT TOOLS (deck slide 14) — the only way the agent touches data
Tool                  Does                       Side effect  Who may call
get_sales_summary     4-wk sales by item         none         LLM
get_inventory         usable stock               none         LLM
get_supplier_quotes   prices + availability      none         LLM
plan_restock          draft plan within budget   draft        LLM
create_supplier_order place approved order       spends       backend, with
                                                              approval token
create_payment_link   Paytm link for invoice     sends        backend, with
                                                              approval token
check_txn_status      verify payment status      none         system only
update_invoice        mark invoice paid          writes       system only,
                                                              after verify
Rules:
- Each tool has Pydantic input/output schemas; inputs from the LLM are
  untrusted candidates and validated.
- The LLM may request a write tool; this only creates an approval
  challenge. Execution happens in /approvals/{id}/confirm with the token.
- check_txn_status/update_invoice run only inside the webhook/verify
  path, never from the LLM.
- OCR text, supplier catalogue text and customer messages are untrusted;
  embedded instructions are ignored. No secrets in model context.

LLM responsibilities: intent (RESTOCK | COLLECT_DUE | BRIEF | UNKNOWN),
extract candidate budget/items/customer, ask clarifying questions,
explain backend-generated plans/briefs in Hindi/English.
Fallback parser (no Sarvam): keywords (stock/saman -> RESTOCK;
payment/udhaar/dues/collect -> COLLECT_DUE; aaj/important/brief -> BRIEF)
+ amount parser (₹5,000, 5000, 5k, "paanch hazaar"); fuzzy match customer
names against invoices.

9. PAYTM ADAPTER (deck slide 10)
Interface: create_link(invoice) -> {provider_order_id, link_url};
fetch_status(provider_order_id) -> {mid, order_id, amount, status, txn_id};
verify_webhook(headers, body) -> bool.
DEMO adapter (default, PAYTM_ENV=demo): returns a DEMO link; "Simulate
customer UPI payment" creates a webhook body signed with a demo key and
posts it to the same /webhooks/paytm handler.
STAGING adapter (PAYTM_ENV=staging): Paytm Payment Links (Create Link)
and Transaction Status API on the Paytm staging host, request bodies
signed with the paytmchecksum library using PAYTM_MID +
PAYTM_MERCHANT_KEY; confirm exact endpoint paths and field names in the
Paytm developer docs at build time. Built and unit-tested with recorded
mock responses; only called "staging-ready" after a real staging call.
Verification path (both modes):
1. Verify webhook signature/checksum; reject if invalid (audit it).
2. Dedupe by provider_event_id (idempotent).
3. Call fetch_status (server-to-server) — never trust the webhook alone.
4. 4-field check: mid == merchant MID, order_id == invoice
   provider_order_id, amount == invoice amount (Decimal, same currency),
   status == success.
5. All pass -> VERIFIED -> PAID via update_invoice; any mismatch ->
   RECONCILIATION_REQUIRED; failure status -> FAILED.

Supplier adapter (SIMULATED): deterministic quotes and shortage;
submit(order) returns per-line ACCEPTED/UNAVAILABLE; simulate_delivery
-> goods-received. Order placement does not imply payment or delivery.

Sarvam adapter (server-side only, timeouts 10 s, text fallback):
STT Saaras (Hindi/Hinglish/English), TTS Bulbul (plan read-back), LLM
chat for intent/explanations, Mayura translation for customer message.
Confirm exact model IDs and audio formats in Sarvam docs at build time.
Voice never blocks the core flows.

11. SECURITY AND PRIVACY
- HTTPS for deployed traffic. Android blocks plain HTTP in release
  builds; for the local-fallback APK pointing at a laptop IP, use a
  separate demo build profile that allows cleartext (expo-build-
  properties) — never in a real release.
- Android app requests RECORD_AUDIO only when the mic is tapped; denied
  -> text input.
- Mobile stores the Supabase session in expo-secure-store, not
  AsyncStorage.
- SARVAM_API_KEY, DATABASE_URL, SUPABASE_SERVICE_ROLE_KEY,
  PAYTM_MERCHANT_KEY only on the server; nothing secret in NEXT_PUBLIC_*.
- Verify Supabase JWT and merchant membership on every protected call;
  every query filtered by merchant_id; RLS enabled as defence in depth.
- CORS restricted to CORS_ORIGINS. Rate-limit assistant, approval and
  webhook endpoints where feasible.
- Redact logs and provider payloads; mask phone numbers.
- Consent: data_connections.consent_granted_at set when a source is
  connected; shown on Connection-status screen.
- Reminders, lending: out of MVP.

12. TEST STRATEGY
Unit: forecast + pack rounding; supplier choice; budget cap; Decimal
totals (4,650 / 3,970 / 4,850); approval hash, expiry, supersede; state
transition tables; webhook signature; 4-field check incl. mismatches;
fallback parser ("₹5,000", "5k", "paanch hazaar" vs "pachaas").
Integration: migrations + seed; transactional approval consumption;
duplicate confirm -> one order; duplicate webhook -> one transition;
cross-merchant access denied; adapter timeout -> FAILED with retry
option.
End-to-end: restock (plan -> approve -> shortage -> replan -> approve 2
-> simulated delivery -> inventory +31); dues (INV-1042 -> link ->
approve -> simulate payment -> PAID); brief; reset restores fixture;
Android app and web dashboard show the same state (approve on phone,
see it on web).

  EXPO_PUBLIC_API_BASE_URL points to the deployed API, plus a local
  fallback build pointing at the laptop.
